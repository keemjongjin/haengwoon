## 시작하며

### 블로그를 하는 이유와 직접 만들게 된 계기

내가 그 동안 공부하면서 프로젝트를 진행하면서 작성한 글들을 내가 원하는 UI를 통해 표현을 하고 싶었고 거기에 더해 내가 예전부터 앨범을 듣고 평점과 후기를 남기던 개인 기록이 따로 있었고, 그걸 어디 흩어진 메모장이 아닌 제대로 된 아카이브에 옮기고 싶다는 생각이 모여 한 도메인 안에서 관리하고 싶다는 생각이 들었다.

기존 블로그 플랫폼들을 사용해봤지만 광고, 낯선 URL 구조 등 매번 어딘가 아쉬운 부분이 있었고, 음악 평점 쪽은 아예 내가 원하는 방식으로 기록하는 플랫폼이 없어 직접 만드는 수밖에 없었다.

재기획 초기 목표는 크게 두가지였다.

- **운영비는 최소한으로** - 조회는 정적/캐시로, 로그인·앨범 등록·투표·댓글처럼 실제로 뭔가를 "쓰는" 요청만 서버리스 함수가 처리한다. 개인 사이트는 트래픽이 크지 않으니 유후 상태에서 비용이 거의 0에 수렴하는 구조가 아니면 계속 유지할 이유가 없다고 생각했다.

- **지속 가능한 웹디자인** - 데이터 전송량, 서버 연산, 클라이언트 기기의 전력 소모를 줄여 디지털 탄소 발자국을 최소화 하는 설계 방식, 최근 AI발전과 빅데이터 세상이 펼쳐짐으로 인해 발전소가 엄청나게 증가할 예정이고 환경적으로도 부정적인 요소가 급증하고 있다. 이후 개발하면서 완벽한 지속 가능한 웹디자인에서는 거리가 멀어지긴 했으나 최대한 리소스를 줄이는 방법으로 벗어나지 않으려 노력했다.

### 기획과 디자인

기획은 재작년 Astro로 제작하던 개인 블로그 프로젝트에서 쓸 만한 부분을 가져오는 걸로 시작했다. 처음부터 다시 정하지 않고, 이미 검증됐던 결정은 그대로 채택하고 부족한 부분만 새로 채웠다. 음악쪽은 초기 기획단계만 있어서 사실상 새로 제작하였다.

블로그 파트는 지속 가능한 웹 디자인(Sustainable Web Design)을 지향점으로 디자인을 했었다. 래퍼런스를 외국 레딧에서 발견한 정말 마음에 드는 고양이 로고가 있는 개인 블로그였는데 그 당시 기록을 안해놔서 아무리 찾아봐도 다시 못찾겠어서 포기했다. 나중에라도 찾게되면 꼭 기록해두겠습니다.
그런데 뭐 음악 아카이브 요소를 넣겠다고 기획에 추가한 이상 완전한 지속 가능한 웹 디자인이란 기획이랑은 거리가 멀어졌지만 최대한 리소스를 줄이기 위한 노력을 했습니다.

## 웹 프레임워크 선택

### Next.js 를 선택한 이유

블로그를 비롯한 콘텐츠 중심의 웹사이트를 구축할 때 흔히 고려되는 선택지는 리액트 기반의 Gatsby였습니다. Gatsby는 정적 사이트 생성(SSG) 생태계에서 오랜 역사를 지녔고, Netlify에 인수된 이후에도 꾸준히 사용되어 왔습니다. 최근에는 아일랜드 아키텍처(Islands Architecture)를 앞세운 Astro 역시 큰 주목을 받고 있습니다. 저 또한 해당 프로젝트를 재작년 Astro는 이용해 제작하다가 다른 프로젝트로 미뤄두었다가 요구사항(음악기록)이 추가되면서 Next.js로 프레임워크를 전환하게 되었습니다.

#### ① 최근 정적 사이트(SSG) 생태계의 트렌드 변화

    최근 몇 년간 정적 사이트와 프론트엔드 아키텍처는 빠르게 진화되고 있습니다.

    1. '순수 정적(Pure SSG)'에서 '하이브리드 렌더링'으로의 전환

    - 과거에는 빌드 시점에 모든 HTML을 생성하는 순수 SSG가 대세였으나, 콘텐츠 양이 늘어날수록 빌드 시간이 급증하는 문제가 있었습니다. 이를 해결하기 위해 정적 캐싱의 속도를 유지하면서도 필요할 떄만 백그라운드에서 페이지를 재생성하는 ISR(Incremental Static Regeneration)이나, 정적 셸과 동적 컴포넌트를 결합하는 PPR(Partial Prerendering) 같은 하이브리드 전략이 표준이 되었습니다.

    2. 아일랜드 아키텍처(Islands Architecture)와 Zero JS 지향

    Astro 등이 이끄는 트렌드로, 페이지 전체를 리액트로 감싸는 대신 대부분을 순수 HTML로 렌더링하고 인터랙션이 필요한 특정 영역(Island)에만 최소한의 자바스크립트를 로드하는 방식입니다. 이를 통해 초기 로딩 속도(LCP, FID/INP)를 극대화하는 콘텐츠 중심 개발이 주목받고 있습니다.

    3. 정적 사이트와 웹 애플리케이션의 경계 붕괴

    단순 정보 전달용 블로그라도 댓글, 좋아요, 실시간 조회수, 사용자 인증, AI 연동 등 동적 인터랙션이 기본 요구사항이 되었습니다. 이에 따라 정적 빌더 단독보다는 서버리스/엣지(Edge) 인프라와 결합된 풀스택 프레임워크의 수요가 크게 늘었습니다.

#### ② 정적 콘텐츠를 넘어 동적 인터랙션과 백엔드 기능이 필요

    기존 블로그 기능뿐만 아니라 평점 관리가 앨범 월드컵, 익명 댓글, 관리자 로그인 처럼 요청마다 DB에 쓰는 기능이 있어 백엔드가 따로 필요했습니다. 초안에는 Astro + Spring Boot on Lambda를 고려하였습니다. 하지만 두개를 따로 구성하여 배포·운영에는 유지관리가 힘들어질 것이라는 판단이었습니다.

#### ② Java/Spring Boot는 서버리스 환경에서 운영 비용과 레이턴시 문제

    Java 기반의 Spring Boot는 전통적인 상시 가동 서버(EC2, 컨테이너 등) 환경에서는 매우 강력하지만, 트래픽이 간헐적인 개인 프로젝트의 Serverless(AWS Lambda) 환경에서는 명확한 한계가 존재

    - 심각한 콜드 스타트(Cold Start) 지연: JVM(Java Virtual Machine)의 초기화 및 Spring 프레임워크의 무거운 Context 로딩(Bean 의존성 주입 등)으로 인해, 요청이 드물 때 발생하는 첫 응답 대기 시간이 수 초 이상으로 길어졌습니다.

    - 최적화 설정의 복잡도: AWS SnapStart나 GraalVM Native Image(Spring Native)를 적용해 콜드 스타트를 완화할 수 있지만, 런타임 제약 사항과 빌드 복잡도, 디버깅 비용이 크게 증가합니다.

    - 풀스택 Node.js 런타임의 가벼움: 반면 Next.js를 Vercel이나 서버리스 기반으로 배포할 경우, 가벼운 Node.js/Edge 런타임을 활용해 매우 짧은 콜드 스타트로 서버리스의 비용 및 확장성 이점을 온전히 누릴 수 있었습니다.

## 프로젝트를 마무리하며

이번 프로젝트를 계획하면서 여러 레퍼런스를 찾아보고 디자인을 했는데, 원하던 모습으로 구현되어 뿌듯합니다. 앞으로도 필요한 기능이나 개선사항이 있으면 꾸준히 업데이트를 해나갈 예정입니다. 기존에 작성한 블로그 글을 옮기려는데 꽤나 미숙한 점이 보여 검토하고 수정해서 다시 업로드를 하려 하는데 꽤나 오랜 시간이 걸릴 것 같아 걱정이 앞서기는 합니다. 앞으로도 개인 학습이나 프로젝트에서 얻은 제 나름의 경험들을 글에 잘 녹여 넣어 공유하는 것을 목표로 계속해서 블로그를 운영해 나가도록 하겠습니다.
